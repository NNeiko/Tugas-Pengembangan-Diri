01. Pendahuluan: Ketika Gambar yang Bagus Saja Ternyata Tidak Cukup

Ketika pertama kali melangkah masuk sebagai mahasiswa Program Studi Teknik Informatika di Universitas Teknologi Bandung, bekal utama yang paling saya percaya diri bukanlah algoritma pengurutan atau struktur data pohon biner, melainkan ketekunan menggambar piksel demi piksel. Sejak awal perkuliahan, meja kerja digital saya lebih akrab dengan kanvas Aseprite dan Krita—merancang sprite sheet karakter 2D, menyusun palet warna atmosferik, hingga memodelkan aset 3D sederhana.

Pada fase awal itu, saya sempat memandang pengembangan game dari kacamata seorang seniman visual: selama animasi berjalan karakter terlihat halus dan pencahayaan latar belakangnya memikat, separuh pekerjaan sudah selesai. Namun, anggapan tersebut runtuh begitu saya mulai memindahkan aset-aset visual itu ke dalam game engine seperti Unity.

Sebuah karakter pixel art yang digambar selama delapan jam tetap hanyalah sekumpulan piksel mati di layar jika tidak ditopang oleh sistem deteksi tumbukan (collision) yang presisi, mesin status animasi (state machine) yang responsif, serta arsitektur kode yang mampu menangani masukan pemain tanpa jeda. Di titik itulah saya menyadari bahwa di balik setiap pengalaman bermain yang terasa mulus, berdiri fondasi rekayasa perangkat lunak yang disiplin.

02. Tekanan 48–72 Jam di Arena Game Jam

Kesadaran teoretis di ruang kuliah berubah menjadi ujian nyali yang sesungguhnya ketika saya mulai terjun ke kompetisi Game Jam tingkat nasional—salah satunya saat membangun game bertema literasi keuangan dalam ajang Zoud GameLab FinLit Jam bersama tim. Dalam format kompetisi yang membatasi waktu pengerjaan hanya 48 hingga 72 jam dari pengumuman tema hingga pengumpulan build akhir, tidak ada ruang bagi perfeksionisme yang berlarut-larut.

Di jam-jam pertama, antusiasme tim biasanya meluap-luap: kami ingin memasukkan puluhan mekanik, sistem dialog bercabang, hingga puluhan variasi aset visual. Namun memasuki jam ke-24, realitas waktu mulai menampar. Saya belajar secara langsung bahwa musuh terbesar dalam Game Jam bukanlah kurangnya ide, melainkan kegagalan mengelola ruang lingkup (scope management).

“Di arena Game Jam, satu mekanik inti yang selesai, stabil, dan menyenangkan untuk dimainkan jauh lebih berharga daripada sepuluh fitur ambisius yang masih rusak sepuluh menit sebelum tenggat pengumpulan.”

Pengalaman ini juga melatih kecepatan komunikasi lintas peran. Karena saya memahami alur kerja artistik sekaligus logika pemrograman, saya belajar menerjemahkan kebutuhan teknis secara pragmatis: kapan sebuah animasi cukup menggunakan empat frame kunci alih-alih dua belas, kapan efek visual bisa diselesaikan lewat interpolasi kode (tweening) daripada menggambar ulang aset, dan bagaimana menjaga agar playable build selalu siap diuji kapan saja.

03. Pelajaran Teknis & Arsitektur Pemrograman Nyata

Dari beberapa siklus pengembangan game dan kompetisi yang saya jalani, ada tiga pelajaran rekayasa perangkat lunak yang paling membekas dan mengubah cara saya menulis kode hingga hari ini.

A. Meninggalkan Skrip “Spaghetti” Menuju Arsitektur Modular (Decoupling)

Pada proyek-proyek pertama di Unity, saya melakukan kesalahan klasik pemula: menumpuk hampir seluruh logika permainan—mulai dari input gerak pemain, perhitungan gravitasi, pengecekan inventori, hingga perilaku musuh—ke dalam satu kelas besar dengan metode Update() yang membengkak ratusan baris. Akibatnya, mengubah satu variabel kecepatan lari saja bisa memicu bug pada sistem deteksi suara musuh.

Saat mengembangkan mekanik stealth berbasis pendengaran AI dan sistem manajemen status pemain, saya mulai menerapkan prinsip pemisahan tanggung jawab (decoupling) menggunakan Interface dan C# Events. Alih-alih membuat skrip pergerakan pemain saling terikat erat dengan skrip penjaga AI, pemain cukup memancarkan sinyal suara (ISoundEmitter) pada radius tertentu, sementara komponen pendengaran AI hanya mendengarkan sinyal tersebut secara independen.

StealthAudioSystem.cs — Pendekatan Modular (Event & Interface) 
using System;
using UnityEngine;

// 1. Kontrak antarmuka agar sumber suara tidak perlu tahu siapa pendengarnya
public interface INoiseListener
{
    void OnNoiseHeard(Vector2 sourcePosition, float intensity);
}

// 2. Komponen kaki pemain hanya bertugas memancarkan radius suara langkah
public class FootstepNoiseEmitter : MonoBehaviour
{
    [SerializeField] private LayerMask listenerLayer;
    private readonly Collider2D[] _hitBuffer = new Collider2D[8];

    public void EmitFootstep(float radius, float intensity)
    {
        // Menggunakan NonAlloc untuk mencegah lonjakan Garbage Collection di Update
        int count = Physics2D.OverlapCircleNonAlloc(transform.position, radius, _hitBuffer, listenerLayer);
        for (int i = 0; i < count; i++)
        {
            if (_hitBuffer[i].TryGetComponent<INoiseListener>(out var listener))
            {
                listener.OnNoiseHeard(transform.position, intensity);
            }
        }
    }
}
using UnityEngine;

// ANTI-PATTERN: Semua logika gerak, animasi, dan AI terikat langsung di satu kelas
public class PlayerAllInOne : MonoBehaviour
{
    public GuardAI[] allGuardsInScene; // Harus di-drag manual setiap tambah musuh!
    public InventoryUI inventoryUI;
    public float moveSpeed = 5f;

    private void Update()
    {
        float moveX = Input.GetAxisRaw("Horizontal");
        transform.position += new Vector3(moveX * moveSpeed * Time.deltaTime, 0f, 0f);

        // Mengecek jarak setiap musuh di setiap frame (sulit di-debug & boros memori)
        if (Mathf.Abs(moveX) > 0.1f)
        {
            foreach (var guard in allGuardsInScene)
            {
                if (Vector2.Distance(transform.position, guard.transform.position) < 6f)
                {
                    guard.isAlerted = true;
                    guard.targetPosition = transform.position;
                }
            }
        }
    }
}

B. Disiplin GDD & Architecture Design Document Sebelum Menulis Kode

Pelajaran berikutnya datang dari pengalaman mengikuti program studi independen Game Development serta tanggung jawab menyusun materi kurikulum di Divisi Game UKM OXIGEN kampus. Ketika harus membimbing rekan-rekan mahasiswa lain membangun game dari nol, saya menyadari bahwa langsung membuka editor kode tanpa rancangan tertulis adalah resep kekacauan.

Penyusunan Game Design Document (GDD) dan Architecture Design Document (ADD)—meski hanya dua atau tiga halaman ringkas—membantu memetakan alur status permainan (game loop), relasi antar kelas, serta daftar aset yang benar-benar dibutuhkan sebelum satu baris kode pun ditulis.

C. Debugging Pragmatis dan Kontrol Versi Git di Bawah Tekanan

Tidak ada proyek game yang luput dari bug menjelang tenggat waktu: mulai dari karakter yang tersangkut di sudut tilemap collider, shader material yang berubah menjadi ungu saat berpindah templat render, hingga konflik scene file pada Git. Dari sini saya belajar membiasakan disiplin atomic commit per fitur kecil serta memanfaatkan cabang (branch) terpisah antara eksperimen mekanik dan integrasi aset visual, sehingga versi stabil selalu terlindungi ketika terjadi kesalahan fatal.

Key Takeaways · Rangkuman Pelajaran Teknis
  • 01. Scope Management adalah Kunci Kelulusan Proyek: Memangkas fitur sekunder sejak hari pertama memastikan inti permainan selesai utuh dan teruji.
  • 02. Decoupling Mencegah Efek Domino Bug: Memisahkan sistem lewat Interface dan Events membuat kode mudah dimodifikasi tanpa merusak modul lain.
  • 03. GDD/ADD Ringkas Menghemat Jam Debugging: Satu jam merancang arsitektur di atas kertas mampu menghemat sepuluh jam merombak kode di tengah jalan.
  • 04. Git Discipline pada Aset Biner & Scene: Pembagian tanggung jawab prefab dan commit terstruktur mencegah konflik saat bekerja dalam tim lintas peran.

04. Refleksi “Learning in Public” & Dampaknya ke Perkuliahan

Hal paling menarik yang saya rasakan setelah rutin membangun game adalah bagaimana konsep-konsep abstrak di ruang kuliah Teknik Informatika tiba-tiba menemukan wujud nyatanya. Mata kuliah Pemrograman Berorientasi Objek (PBO) tidak lagi terasa sekadar latihan membuat kelas Hewan atau Kendaraan, melainkan menjadi alat nyata untuk merancang hierarki entitas dan perilaku senjata dalam game.

Begitu pula dengan Struktur Data dan Algoritma: memilih antara List, Dictionary, atau Object Pooling berdampak langsung pada kestabilan frame rate saat puluhan proyektil muncul bersamaan. Konsep Kecerdasan Buatan (AI) pun terasa hidup ketika saya mengimplementasikan Finite State Machine dan pencarian jalur (pathfinding) bagi agen musuh agar dapat berpatroli dan mengejar pemain secara alami.

Bagi saya, mempraktikkan learning in public—dengan mendokumentasikan catatan pengembangan, membagikan proses pembuatan aset maupun arsitektur kode, serta menyusun modul ajar bagi mahasiswa lain—bukanlah ajang untuk memamerkan hasil akhir yang tampak sempurna. Justru sebaliknya, ini adalah cara paling jujur untuk merawat akuntabilitas diri: memaksa saya memahami suatu konsep cukup dalam hingga mampu menjelaskannya kembali dengan bahasa yang jernih dan bermanfaat bagi orang lain.

05. Penutup: Menjembatani Rasa Ingin Tahu dan Disiplin Rekayasa

Perjalanan dari sekadar menggambar piksel di kanvas 2D hingga merancang arsitektur kode C# yang terstruktur mengajarkan saya bahwa identitas seorang pembelajar di bidang teknologi tidak harus terkotak-kotak. Kepekaan visual membantu saya merancang pengalaman pengguna yang manusiawi, sementara disiplin rekayasa perangkat lunak memberi saya alat untuk mewujudkan ide tersebut menjadi sistem yang andal.

Untuk rekan-rekan sesama mahasiswa Teknik Informatika yang mungkin masih ragu memulai proyek di luar tugas rutin kelas: mulailah dari ruang lingkup sekecil mungkin, ikuti satu kompetisi atau bangun satu prototipe nyata, lalu tuliskan apa yang Anda pelajari darinya—termasuk setiap kesalahan yang Anda temui di sepanjang jalan. Sebab sering kali, kemajuan terbesar kita justru lahir dari catatan jujur tentang bagaimana kita bangkit dari kode yang sempat gagal berjalan.
